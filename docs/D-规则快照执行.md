# D：按固定规则版本执行审核

## 解决的问题

设计书要求正式审核只读开始时选定的规则快照。此前报告记录了 `rule_version_id`，但完整性、时间、格式、内容检查，以及整改建议和模型提示词仍查询实时规则表。一次审核可能混用多个版本。

本次将 `RuleVersion.snapshot` 转成与数据库对象分离的只读规则集。四类检查、材料类型、术语、关注词、整改模板和提示词均来自同一个规则集。即使审核期间管理员修改规则，本次结果仍依据开始时的版本；之后启动的审核使用新版本。

## 行为与兼容性

- 正式审核由工作进程实际开始执行时选定最新规则版本，排队接口不新增参数。
- 固定九组规则；快照缺组或清单引用不存在的材料类型时明确失败，不回退查询实时规则。
- 检查需要即时解析材料时，分类、节点抽取、节点合并也接收同一规则集。
- 上传后的独立解析任务、实时完整性预览和规则试运行继续使用当前配置。
- 日期按北京时间在审核开始时取一次。日历、周期尾段阈值、批次结束日和分类阈值也只取一次。日历保存在报告上下文中，因为设置修改本身不会发布规则版本。
- 新报告在 `timeline_snapshot.evaluation_context` 中保存时间、日历、规则版本 ID 与 SHA-256；`node_inputs` 保存本次时间检查使用的节点值，包括序列、学时和冲突状态。
- 保留原有 `nodes` / `derived` 字段，报告接口无需改动。旧报告缺少上下文仍可读取，不补写、不修改历史规则版本，不需要数据库结构迁移。
- 模型请求使用固定版本的提示词；连接地址、密钥等运行配置不写入规则集或报告上下文。

## 验证

在后端目录运行：

```bash
python -m pytest -q
```

新增用例覆盖：V1 要求一份、V2 要求两份；模拟审核中途发布 V2；深层规则参数不可变；九组快照缺失时拒绝执行；时间规则、日历、检查日期、格式规则、术语、关注词、整改模板、模型提示词均使用固定值；即时解析参数传递；旧报告与新报告的详情兼容；实时预览仍读取当前配置。测试替身禁止正式审核查询九类实时规则表。

另在 `test_review_regressions.py` 中补充 PostgreSQL 用例：发布两个真实版本、按旧版/新版审核、重新读取报告 JSONB、读取历史报告。沿用仓库已有隔离测试库机制：仅在设置 `TEST_DATABASE_URL` 后执行，在随机测试 schema 中运行并清理。

## 团队验收步骤

1. 在测试环境使用组织部账号，将某个阶段的一项必交材料设为固定一份，保存为 V1；学生提交一份该材料。
2. 发起仅规则审核，等待报告 A 完成，记录版本号，确认该项“应交 1、已交 1”。
3. 修改该项为固定两份，保存为 V2；重新打开报告 A，应仍显示 V1 和“应交 1”。
4. 再次发起审核，报告 B 应显示 V2 和“应交 2、已交 1、缺 1”。
5. 查看报告详情接口，确认两份报告分别记录自己的 `evaluation_context`；已有历史报告仍可正常打开。配置测试数据库后执行全部回归，完成持久化验收。

## 本次边界

规则快照固定的是审核规则。重算时还应提供相同的材料版本、解析文本/人工校正、人员信息、阶段和节点等业务输入。已完成解析的材料继续使用现有解析结果，不自动对全部历史材料重新抽取节点；本次新增 `node_inputs` 用于核对实际输入。

日期和日历可追溯不代表外部模型能逐字重现输出。旧报告未记录检查上下文时，无法恢复当时的全部日历取值。历史报告中 `upload_date_policy=CHECK_DATE` 的结果仍按原样保存。自 2026-10-26 的修复起，新审核的 R-T21 逐条比较节点日期与其材料版本的北京时间上传日；缺少来源或上传日期时标记为跳过，不再借用检查日期。新报告上下文为 `format_version=2`、`upload_date_policy=MATERIAL_VERSION_UPLOADED_AT`，`date_inputs` 保存各来源日期、版本和上传时间。

内部 `run_check` 支持指定规则版本和已构造的检查上下文，供回归验证使用；没有新增对外“重放历史报告”接口。规则新增、修改、删除、导入及初始化现在在写入前取得同一数据库事务级发布锁，版本号分配和快照发布随提交或回滚一起完成。并发修改已读取的条目会在取得锁后重新读取。
