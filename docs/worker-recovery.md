# 后台任务中断恢复

Worker 启动时检查超时任务，并由独立线程持续检查。检查间隔为心跳超时的三分之一，最短 1 秒、最长 30 秒；执行线程全部繁忙时检查仍会继续。每轮最多处理 100 个超时任务。重启时尚未超时的任务会在之后的检查中恢复。

正在执行的业务事务持有任务行的 `FOR KEY SHARE` 锁，独立心跳可以正常更新这行。恢复使用 `FOR UPDATE SKIP LOCKED`，跳过仍受执行事务保护的任务。因此，仅心跳延迟不会触发并行重跑；实际进程退出、数据库连接断开或事务回滚释放锁后，任务才具备恢复条件。

每次领取使用 `(id, attempts, started_at)` 标识执行代次，领取结果先提交。新的 `started_at` 严格晚于上一次，手工重试重置 `attempts` 也不会复用代次。开始执行、心跳、成功结果和失败记录均校验代次，旧尝试在回滚后迟到的数据库写入会被丢弃。达到 `max_attempts` 的中断任务标记失败，不再自动排队。

批量 AI 检查已拆出子任务的父任务保持等待状态，恢复只汇总子任务进度，不重复拆分或消耗父任务重试次数。子任务正常结束或被恢复为最终失败时，都会更新父任务。

## 事务约定与边界

- 任务处理函数共用 worker 的业务事务，不得自行提交外层事务；运行时会阻止这种提交。现有解析、AI 检查、批量上传和导出路径均由 worker 提交。内部保存点可以使用。
- 重试提供中断恢复和数据库结果隔离，不保证文件写入、OCR 子进程或外部模型请求只执行一次。数据库连接已丢失时，旧外部调用可能仍在完成；处理函数应尽量让这类操作可重复或采用单独的幂等机制。
- 此次锁保护依赖新版 worker。升级时先停止旧版 worker，再启动新版，避免混用不持有执行锁的旧进程。
- 保持数据库事务和连接存活的真正卡死任务会被安全跳过；需要排查并终止对应执行进程或数据库会话，而不能仅凭漏心跳并行启动另一份工作。

`backend/tests/test_worker_recovery.py` 使用 `TEST_DATABASE_URL` 下随机创建的隔离 PostgreSQL schema，验证周期恢复、并发锁、心跳、连接中断、旧代次结果隔离、重试上限和批量父任务；结束后删除该 schema。
