## 先运行前端

用 VS Code 打开交付包中的 `whu-party-review` 文件夹。在终端逐行执行：

```powershell
cd frontend
npm.cmd ci
npm.cmd test
npm.cmd run test:ui
npm.cmd run dev
```

终端显示的本机地址用于访问开发界面。正常业务页面需要后端在线；后端环境和演示账号沿用 `docs/RUN.md`。只有前端运行时，登录或材料查询失败属于预期，不会使用假数据冒充成功。

如果 A 的后端运行在本机其他端口，在启动前设置：

```powershell
$env:BACKEND_PORT = "8001"
npm.cmd run dev
```

`BACKEND_PORT` 仅更改本机代理端口，不能填写另一台电脑的 IP。连接团队服务器时由 E 按现有请求封装及部署方式配置，不要把数据库密码或模型密钥填进前端。

## 和 A B D 一起做真实验收

使用虚构材料，按顺序在同一个测试服务器操作。每一步同时核对界面结果与后端返回记录，不能只凭提示文字判定成功。

1. 学生登录，进入“我的材料”，上传一份可复制文字的 PDF。确认列表出现真实记录，解析任务结束，预览能够打开。
2. 发起自查。检查进行中按钮不能重复点击，完成后显示报告、完整性和问题；若报告过期，提交按钮给出重新自查提示。
3. 对阻断问题填写说明或补交版本，再提交审核。确认学生状态进入支部审核，审核员待办出现同一提交包。
4. 审核员点击问题，核对原文版本、页码和高亮。确认/修改问题，填写意见后退回。
5. 学生进入整改中心，查看通知，上传新版本并保存说明。确认响应携带真实版本编号，解析期间不能重提。
6. 重新提交，检查复核任务及“已解决、未解决、新增”结果。分别使用相应层级账号继续通过，最后由组织部备案。
7. 备案后确认材料不能上传、历史版本不能修改；学生不能访问他人材料；非当前层级审核员没有修改入口且后端拒绝越权操作。
8. 上传一个含匹配和未匹配文件的 ZIP。确认识别完成不会被显示成已入库；指定归属并导入，故意制造一项失败，确认重试请求不包含已成功项。
9. 分别模拟断网、文件缺失、解析失败和 AI 任务失败，确认提示真实原因并可重试，不能显示“无问题”冒充成功。

## 已核实的接口边界

- A 控制提交、审核、备案和权限；前端不替代后端状态机。当前后端允许人工处理过的阻断问题单份通过，但批量通过仍禁止有效阻断问题。需要统一该业务规则时，由 A、D 共同确认，不能只改前端。
- B 的 ZIP 识别任务只返回匹配信息，确认接口才真正导入；当前确认接口使用档案的当前阶段。页面已说明此行为。网络中断导致结果不明确时先核对档案记录，后端入库幂等仍由 B 保障。
- B 的时间轴来源返回 `version_no`，前端先查版本列表再找到真正的版本 ID，不把版本号当 ID。
- D 的报告是否过期及问题数据以接口为准。草稿要求有效报告；退回后的旧报告可以重提，由 A 自动触发复核。
- OCR、模型服务及其降级结果沿用后端能力，本阶段没有新增或训练模型。首轮交付时 Windows 安装包、公共设置和部署交由 E、A 负责；后续按需求新增的桌面交付见 Windows 使用说明，团队合并时仍需 E、A 审阅。

## 交给 E 合并

以下命令针对首轮补丁的原始基线，保留供历史交付核对；最新综合修改应在最新 `dev` 上逐文件合并并提交功能分支 PR，不要将不同基线补丁直接叠加。应用首轮随包提供的 `C前端改动补丁.patch` 时，先保存自己的工作区，再从最新 `dev` 创建功能分支：

```powershell
git switch dev
git pull --ff-only
git switch -c feature/c-student-review
git apply --check "补丁的实际路径\C前端改动补丁.patch"
git apply "补丁的实际路径\C前端改动补丁.patch"
cd frontend
npm.cmd ci
npm.cmd test
npm.cmd run test:ui
npm.cmd run build
```

如果 `git apply --check` 提示冲突，说明团队代码已有变化；由 E 对照补丁逐文件合并，不使用强制覆盖。源码压缩包也提供全部当前文件，可用于独立运行或人工对照。

E 重点检查 `frontend/package.json`、锁定文件、公共上传组件和阶段组件；A、B、D 按上一节验收接口。合并时遵循原仓库的 PR 流程。构建产物、`node_modules`、个人 `.env` 和材料文件不要提交。
